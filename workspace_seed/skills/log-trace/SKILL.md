# Log Trace

## 적용 범위

캠페인 발송 흐름과 결과 집계 흐름의 이상을 분석한다. 운영 데이터 변경, 배치 재실행, 소스 수정은 하지 않는다.

## 추적 절차

1. 문의에서 캠페인 ID, 날짜, 증상을 정리한다. 증상을 `발송 흐름 문제(발송 안 됨·일부 발송·대상 수)`와 `결과 흐름 문제(결과 화면 값 이상)`로 나눈다.
2. 발송 흐름이면 캠페인 정보를 조회한다. 해당 날짜의 B01~B04 로그에서 캠페인의 시작·종료 줄을 찾고 단계별 건수와 처리 시간을 표로 만든다. 건수가 줄거나 종료 줄이 없거나 처리 시간이 비정상적으로 긴 첫 단계를 문제 후보로 둔다.
3. 결과 흐름이면 화면에서 출발한다. 화면이 읽는 테이블, 그 테이블을 쓰는 배치, 배치가 읽는 테이블 순으로 관계를 거슬러 올라가고 각 테이블의 적재 상태를 확인한다.
4. 후보 지점의 로그에서 `ERROR`, `WARN`, 롤백, `skip`, 건수 0을 검색한다. ERROR가 없어도 건수와 DEBUG 로그를 확인한다.
5. 자정을 넘긴 처리, 처리일자와 발송일자의 차이 등 시간 관련 이상을 확인한다.
6. 정상 날짜 로그와 처리 시간·건수를 비교해 평소와 다른 점을 수치로 확인한다.
7. 발송 이력과 집계 테이블로 로그 건수를 교차 확인한다.
8. 관련 소스와 변경 이력을 확인한다.
9. 같은 날 다른 캠페인도 영향을 받았는지 확인하고, 근거 없이 범위를 일반화하지 않는다.
10. 과거 장애 이력을 검색해 같은 점과 다른 점을 비교한다.
11. 원인 후보를 근거 강도 순으로 정리한다. 증상과 시간·대상이 맞지 않는 ERROR는 후순위로 둔다. 결함이 없으면 as-is 동작을 설명하고 확인할 점을 제안한다.
12. 자료가 부족하면 멈추고 필요한 자료를 구체적으로 요청한다.
13. `templates/report_template.md` 양식으로 보고서를 작성하고 개인정보 마스킹을 확인한다.

## 실행 보고서 자동 저장

S1~S4 시나리오 분석이면 최종 보고서를 완성한 직후 저장 위치를 다시 묻지 말고 저장한다. 단순 질의나 시나리오 분석이 아닌 요청은 저장하지 않는다.

- S1은 새 평가 세트다. `execute`로 `TZ=Asia/Seoul date +%Y%m%d-%H%M%S` 값을 얻고 `runs/<평가시각>/` 폴더를 만든다. 폴더명은 KST 기준이다. 그 이름을 `runs/.current-session`에 기록하고 `runs/<평가시각>/S1.md`에 보고서를 쓴다.
- S2~S4는 `runs/.current-session`을 읽어 같은 폴더에 각각 `S2.md`, `S3.md`, `S4.md`로 저장한다. 폴더를 새로 만들거나 이전 보고서를 덮어쓰지 않는다.
- 포인터가 없거나 대상 시나리오 파일이 이미 있으면 덮어쓰지 않는다. 새 평가 세트를 시작해야 하면 사용자에게 S1부터 새 대화에서 실행하도록 안내한다.
- 저장 후 `ls`로 경로와 파일을 확인하고 저장 경로만 알린다.
## 도구 선택

## 도구 선택

- 로그는 `/input/logs/`의 파일 도구로 읽는다.
- 배치, 캠페인, 발송 이력, 집계, 관계, 소스, 변경 이력, 과거 장애는 조회 도구만 사용한다.
- 한 번에 넓게 읽기보다 먼저 검색하고, 근거가 되는 필요한 줄만 읽는다.
- 조회 결과가 없으면 다른 값을 추측하거나 평가 파일을 찾지 않는다.

## 근거 표기

- 로그: `파일명:줄번호`
- 소스: `클래스명:줄번호`
- 확인된 사실은 `[확인]`, 추정 또는 후보는 `[추정]`으로 표시한다.
- 로그 원본의 시각 형식을 그대로 유지한다.
