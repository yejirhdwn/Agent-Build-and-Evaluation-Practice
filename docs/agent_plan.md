# 나만의 에이전트 기획서: 로그 기반 원인 추적 에이전트

- 과정: LLM 기반 Agent 구축 및 평가 실습 (09/30\~10/01)
- 작성자: 권예지

---

## 0. 기획 배경 및 진행 방향

### 현재 업무 환경

현재 업무는 VDI 환경에서 이루어지며, 소스·로그 등 업무 데이터는 모두 보안 관리 대상이라 외부로 반출할 수 없다.

### 선행 프로젝트

고객사와 함께 VDI 내부에서 소스를 내려받아 AI를 적용하고, 소스를 구조화해 Graph DB 등을 구축하는 프로젝트를 진행한 경험이 있다. 즉, VDI 내부에도 소스 구조와 관계를 조회할 수 있는 기반이 마련되어 있다.

### 이번 실습의 방향

이번 실습은 내부 소스를 외부로 가지고 나와 업무 에이전트를 만드는 것이 아니라, 외부(Codespace)에서 에이전트 설계를 탄탄하게 만든 뒤 그 설계를 VDI 내부로 가지고 들어가 적용하는 것을 목표로 한다. 이후 해당 구조를 실제 DB(Graph DB, 발송 이력 DB 등)와 연결해 실제 업무에 활용할 수 있도록 한다.

- **외부(Codespace)에서 할 일:** system prompt, AGENTS.md, skill, 도구 인터페이스를 설계하고 목업 데이터로 실행·검증하며 개선
- **VDI로 가지고 들어갈 것:** 검증된 에이전트 설계와 코드 구조 (데이터는 가지고 나오지 않음)
- **VDI 내부에서 할 일:** 목업 데이터를 읽던 도구를 실제 DB·로그·소스 조회로 교체하여 연결

### 진행 방식에 따른 제약과 대응

| 구분 | 제약 | 대응 |
|---|---|---|
| ① | 실제 데이터를 사용할 수 없어 목업 데이터로 진행해야 한다. | 실제 채널 발송 흐름의 구조(배치 단계, 모듈 연결, 로그 형식)를 반영한 가상의 로그·소스·장애 이력을 만들어 사용한다. 실제 값과 개인정보는 포함하지 않는다. |
| ② | MCP 등 외부 시스템 연결 도구를 붙일 수 없다. | DB 조회, 소스 탐색, 이력 검색 기능을 목업 파일을 읽는 커스텀 도구로 대신 구현한다. 도구의 이름·입력·출력 형식은 실제 연결을 가정해 설계하여, VDI 내부에서는 도구 내부 구현만 교체하면 되도록 한다. |
| ③ | 외부 환경의 LLM·라이브러리가 VDI 내부 환경과 다를 수 있다. | 특정 모델에 의존하는 설정은 최소화하고, 반입 전 VDI 내부에서 사용 가능한 모델과 라이브러리 환경을 확인한다. |

> 목표는 외부에서 완성된 에이전트를 만드는 것이 아니라, 내부에 가지고 들어가 실제 데이터와 연결했을 때 바로 동작할 수 있는 검증된 설계를 만드는 것이다.

## 1. 나의 업무 나열하기

### 업무 ① 현업 요청 기반 화면·기능 개선

| 항목 | 내용 |
|---|---|
| 입력 | 요청서 또는 메일 기반 요청, 관련 화면·기능의 기존 소스, 화면/테이블 정의서 |
| 출력 | 수정 소스, 반영 결과, 요구사항 확인 회신 메일(as-is 설명 + 반영 방향 확인) |
| 반복도 | 수시 (주 단위) |
| 판단 난이도 | 중간 |
| 힘든 점 | 수정 시 영향 범위 확인, 반영 가능한 요구인지 판단, 두루뭉실한 요구사항을 현재 동작(as-is) 기준으로 정리해 어떻게 반영하길 원하는지 되묻는 회신 작성 |

### 업무 ② 채널 발송 연계 흐름 분석·점검

| 항목 | 내용 |
|---|---|
| 입력 | 배치 로그, 배치 잡 목록·스케줄, 연계 모듈 소스, 발송 이력 데이터 |
| 출력 | 흐름 정리, 이슈 원인 분석 |
| 반복도 | 이슈·문의 발생 시 |
| 판단 난이도 | 중간 |
| 힘든 점 | 배치·모듈이 흩어져 있어 어느 단계에서 막혔는지 연결고리를 추적하기 어려움 |

### 업무 ③ 장애 대응

| 항목 | 내용 |
|---|---|
| 입력 | 에러 로그, 관련 소스, 과거 장애 이력·조치 기록 |
| 출력 | 원인 파악, 조치, 장애 보고/조치 내역 정리 |
| 반복도 | 수시 |
| 판단 난이도 | 중간\~높음 |
| 힘든 점 | 범위가 큰 레거시 시스템에서 장애 위치를 찾으려면 전체 소스와 로그를 뒤져야 하고, 담당자 역량에 따라 대응 속도와 품질 편차가 큼 |

## 2. 에이전트로 도움받을 부분 찾기

찾아볼 관점: 정보 찾기, 초안 작성, 형식 변환, 오류 검토, 반복 실행, 결과 정리

### 업무 ① 현업 요청 기반 화면·기능 개선

- 요청서/메일에서 요구사항 항목 추출 및 모호한 부분 표시 (정보 찾기, 오류 검토)
- 관련 화면·기능의 기존 소스를 찾아 현재 동작(as-is) 요약 (정보 찾기, 결과 정리)
- 수정 대상 소스를 호출하는 곳, 참조 테이블 등 영향 범위 후보 표시 (정보 찾기, 오류 검토)
- as-is 설명과 확인 질문을 담은 현업 회신 메일 초안 작성 (초안 작성)

### 업무 ② 채널 발송 연계 흐름 분석·점검

- 배치 로그에서 에러, 지연, 건수 불일치 구간 추출 (정보 찾기, 오류 검토)
- 배치 잡 목록과 모듈 소스를 따라 발송 흐름을 단계별로 정리 (결과 정리, 형식 변환)
- 흐름 중 로그가 끊기거나 건수가 줄어드는 지점을 원인 후보로 표시 (오류 검토)
- 흐름도와 원인 분석 결과를 정해진 형식의 문서 초안으로 작성 (초안 작성)

### 업무 ③ 장애 대응

- 에러 로그에서 핵심 에러 메시지, 발생 시각, 관련 클래스/모듈 추출 (정보 찾기)
- 에러와 관련된 소스 위치 탐색 및 호출 흐름 요약 (정보 찾기, 결과 정리)
- 과거 장애 이력에서 유사 사례와 당시 조치 내용 검색 (정보 찾기)
- 원인 후보와 확인 순서를 체크리스트로 제시 (결과 정리)
- 장애 보고/조치 내역 초안 작성 (초안 작성)

> 세 업무에서 공통으로 반복되는 부분은 "로그/요청에서 핵심 추출 → 관련 소스 찾기 → 흐름 요약 → 문서 초안"이다. 실제 소스 수정, 운영 반영, 조치 실행은 판단과 책임이 필요한 영역이므로 사람이 담당하고, 에이전트는 앞단의 찾고 정리하는 구간을 보조한다.

## 3. 만들 에이전트 고르기

### 선택한 에이전트: 로그 기반 원인 추적 에이전트

업무 ② 채널 발송 연계 흐름 분석·점검과 업무 ③ 장애 대응은 모두 로그를 출발점으로 흩어진 배치·모듈·소스를 따라가며 문제 지점을 찾는 일이라, 하나의 에이전트로 묶는다. 두 업무의 차이는 범위(특정 발송 흐름 vs 레거시 시스템 전체)이므로, "로그 기반 원인 추적 에이전트"를 만들고 첫 적용 범위를 채널 발송 연계로 한정한다.

채널 발송 흐름은 범위가 정해져 있어 배치 목록, 모듈 연결 관계, 자주 발생하는 이슈를 skill/reference로 정리하기 쉽고 결과 검증도 쉽다. 이후 다른 영역의 흐름 지식을 skill로 추가해 장애 대응 전반으로 확장한다. 숙련자의 추적 순서를 skill로 정리해 두면 담당자 역량에 따른 대응 편차도 줄일 수 있다.

**PoC 주제:** 채널 발송 배치 로그를 입력하면, 발송 흐름상 어느 단계에서 문제가 발생했는지 추적하고 원인 후보와 확인 순서를 정리한 분석 보고서 초안을 만든다.

### 입력

이번 실습에서는 아래 입력을 모두 목업 데이터로 준비한다.

- 채널 발송 배치 로그 (에러 로그 포함)
- 배치 잡 목록·스케줄
- 연계 모듈 소스
- 발송 이력 데이터
- 과거 장애 이력·조치 기록

### 도구 / MCP

- **파일 읽기:** 로그, 배치 목록, 과거 장애 이력 문서 읽기
- **텍스트 검색:** 로그에서 에러·시각·배치명 추출, 소스에서 클래스·메서드·호출 위치 탐색
- **표 계산:** 단계별 처리 건수 비교로 누락·불일치 지점 확인
- **문서 작성:** 흐름 정리 및 원인 분석 보고서 초안 작성
- **MCP:** 이번 실습(Codespace)에서는 사용하지 않음. 아래 기능은 목업 파일을 읽는 커스텀 도구로 대신 구현하고, VDI 내부 적용 시 실제 연결로 교체

- 발송 이력 조회 → VDI 내부 발송 이력 DB 연결
- 연계 모듈 소스 탐색, 호출 관계 확인 → VDI 내부 소스 및 Graph DB 연결
- 과거 장애 이력 검색 → VDI 내부 장애 이력·조치 기록 연결

### 출력

- 발송 흐름 정리 (배치/모듈 단계별 처리 흐름)
- 문제 발생 지점과 근거 로그
- 원인 후보 및 확인 순서 체크리스트
- 유사 과거 장애 사례와 당시 조치
- 분석 보고서 초안

## 4. 반드시 지켜야 하는 규칙

### 금지할 행동

- 로그, 소스, 이력 데이터에 없는 내용을 사실처럼 쓰지 않는다. 배치명, 시각, 건수, 에러 코드는 원본에 있는 값만 사용한다.
- 원인은 확정하지 않고 반드시 "원인 후보"로만 표시한다.
- 소스 수정, 배치 재실행, 데이터 변경 등 운영 환경에 영향을 주는 조치를 직접 실행하지 않는다. 조치는 제안까지만 한다.
- DB는 조회만 하고 쓰기·수정·삭제 쿼리는 실행하지 않는다.
- 고객 개인정보(이름, 연락처 등)를 보고서에 그대로 옮기지 않는다. 필요한 경우 마스킹한다.

### 확인할 조건

- 로그가 중간에 끊기거나 필요한 파일이 없으면 추측으로 채우지 말고 어떤 자료가 더 필요한지 요청한다.
- 원인 후보가 여러 개면 근거의 강도 순으로 정렬하고, 근거가 약한 후보는 약하다고 명시한다.
- 과거 장애 사례를 인용할 때는 현재 상황과 같은 점과 다른 점을 함께 적는다.
- 최종 원인 판단과 조치 실행은 담당자가 확인·승인한 뒤 진행한다.

### 출력 형식

- 보고서는 지정된 순서를 따른다: ① 요약 → ② 발송 흐름 정리 → ③ 문제 발생 지점과 근거 로그 → ④ 원인 후보 → ⑤ 확인 순서 체크리스트 → ⑥ 유사 과거 사례
- 모든 판단에는 근거가 된 파일명과 로그 라인(또는 소스 위치)을 함께 적는다.
- 시각은 로그 원본 형식 그대로 표기한다.
- 추정한 내용과 로그로 확인된 내용을 구분해서 표시한다.
