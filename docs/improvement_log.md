# Meta-Harness 개선 사이클 기록

개선 주체는 `harness-improver` 그래프(방식 A)다. 각 사이클을 가설 → 변경 → 결과 → 판정 순서로 기록한다. 판정의 기본값은 무승부다.

이름 정리:

- **원본 에이전트**(baseline, git tag `baseline-v0`): 1일차 에이전트 그대로
- **원본 1차 측정**: 처음 실행·채점한 기준 점수(`runs/20261001-152522`)
- **원본 2차 측정**: 같은 원본을 개선 에이전트가 다시 실행한 결과(`runs/20261001-154636`)
- **개선안 1**(variant `v1`): 원본을 복제해 log-trace 스킬 한 줄을 고친 수정본(`runs/20261001-155256`)

### 진단

- 원본 1차 측정과 원본 2차 측정 모두 S2 "영향 범위 판단"이 False였다. 두 번 다 같은 항목이 실패했으므로 재현되는 약점으로 봤다.
- S3는 첫 실행 6/9, 재실행 9/9였다. 같은 원본 에이전트에서도 시나리오 하나가 3개 항목만큼 흔들린다. 이 정도가 실행 간 노이즈 수준이다.
- trace 지표: 같은 도구·인자 반복 0, 실패 재시도 0, SKILL 선독, eval 접근 0, 쓰기성 명령 0. 작업 방식 자체의 낭비는 크지 않았다.

### 가설과 변경 (노브: log-trace 스킬, 1줄)

> 영향 범위를 쓰기 전에 다른 캠페인을 실제로 조회해 확인하게 하면, 영향 범위를 좁히거나 넓히는 오류가 줄어든다.

```diff
-9. 같은 날 다른 캠페인도 영향을 받았는지 확인하고, 근거 없이 범위를 일반화하지 않는다.
+9. 영향 범위를 보고서에 쓰기 전에 반드시 조회 도구로 확인한다. 같은 날 또는 인접 날짜의 다른 캠페인을 실제로 조회(캠페인 정보·집계·로그)해 동일 증상 여부를 근거로 확정한다. 조회 없이 다른 캠페인이 같은 문제라고 쓰지 않고, 미확인이면 '확인 필요'로만 표시한다. 근거 없이 범위를 일반화하지 않는다.
```

특정 캠페인 ID·수치·줄번호가 없는 일반 원칙이라 과적합 검사를 통과했다.

### 판정: 무승부 → 반영(promote)하지 않고 원본 에이전트 유지

- 겨냥한 S2 "영향 범위 판단"은 개선되지 않았다.
- S3에서 항목 회귀 2건, S4에서 pairwise 패배가 있었다. 개선과 회귀가 섞이면 무승부다.
- S1·S2의 pairwise 우세는 반복 1회뿐이라 재현성을 확인하지 못했다. S3가 나빠진 것도 원본 자체의 흔들림 범위(6/9\~9/9) 안이라 개선안 1 탓이라고 단정할 수 없다.

### 다음 가설 (개선안 2 후보)

- S2 실패의 실제 원인은 "조회를 안 해서"보다 "어느 날짜 범위의 집계가 영향을 받는지 계산하지 않아서"일 가능성이 높다. 변경 시점 이후 실행된 집계 배치가 어떤 발송일 캠페인을 집계했는지 배치 이력으로 역산하라는 원칙(결과 흐름 전용)을 시험한다.
- 노이즈가 커서, 실패한 시나리오만 3회 반복하는 방식으로 판정 비용을 줄인다.

### 너무 오래 걸린 부분과 개선 방향

고도화 뒤에도 사이클 한 번이 오래 걸렸다. 원본 2차 측정부터 개선안 1의 1번째 실행까지 약 13분이 걸렸다. 2번 반복을 끝까지 돌렸다면 개선안 1에만 10분 이상 더 걸렸을 것이다. LangSmith에서는 개선 에이전트 세션이 하나의 긴 trace로 쌓였다. 처음 시도에서 강제로 끝낸 실행도 종료되지 않은 trace로 남았다.

| 원인 | 다음에 이렇게 개선 |
|---|---|
| 개선 에이전트가 원본을 매번 새로 실행 | 원본 1차 측정 결과를 `suite-import`로 등록해 재사용하고, 노이즈 측정이 필요할 때만 재실행 |
| `--repeat N`이 S1\~S4 전체를 반복 | 접전이거나 바뀐 시나리오만 반복(`--scenarios`) |
| 실행·채점·pairwise가 하나의 `execute` 호출 안에서 동기 실행되고, 한 trace가 수십 분 이어짐 | 평가 세트 실행을 백그라운드 작업으로 분리하고 상태를 조회하는 방식(`run --suite --detach`, `status`)으로 바꾸고, 사이클마다 trace를 나눔 |
| 시나리오별 실행 시간 편차(40\~110초)와 긴 보고서 | 시나리오 deadline을 짧게 잡고, 초과 시 부분 기록으로 판정 |
| pairwise가 시나리오당 2회 호출 | 항목 판정이 같은 시나리오는 pairwise 생략 |
| 강제 종료 시 trace가 열린 채로 남음 | 종료 신호에서 `wait_for_all_tracers()`로 trace를 닫고 종료 |
