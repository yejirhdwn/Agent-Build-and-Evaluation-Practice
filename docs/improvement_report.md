# 로그 추적 에이전트 고도화 보고서 (초안)

- 과정: LLM 기반 Agent 구축 및 평가 실습 Day 2 Final 실습
- 대상: 로그 기반 원인 추적 에이전트(`deepagent` 그래프, 모델 `moonshotai/kimi-k3`)
- 기준점: git tag `baseline-v0`, 기준 점수 `runs/20261001-152522/baseline`

## 1. 개요

Day 1에 만든 로그 추적 에이전트를 세 단계로 고도화했다.

| 단계 | 한 일 | 결과물 |
|---|---|---|
| Observation | LangSmith 트레이싱, 시나리오 메타데이터, 작업 방식 지표 | `observability.py`, `eval/run_scenarios.py`, `eval/trace_metrics.py` |
| 평가 세트·Judge | 기존 S1~S4를 Dataset으로 올리고, 수동 9개 항목 판정을 LLM Judge로 전환 | `eval/judge.py`, `eval/rubric.md`, Dataset `log-trace-eval-s1-s4` |
| Meta-Harness | 별도 개선 에이전트가 격리 복제본으로 실행·수정·비교 | `harness_improver.py`, meta-harness `--suite` 모드, `docs/improvement_log.md` |

핵심 원칙은 강의 결론인 "평가가 개선의 엔진이 된다"이다. 하네스를 손으로 고치지 않았다. 개선 에이전트가 스킬을 읽고 CLI로 자기 복제본을 실행하고, Judge 점수와 trace 지표를 근거로 판정하게 했다.

## 2. Observation 구성

### 2.1 트레이싱

- `.env`의 `LANGSMITH_TRACING`·`LANGSMITH_API_KEY`·`LANGSMITH_PROJECT=log-trace-agent`·`LANGSMITH_ENDPOINT`만으로 동작한다. 코드에 프로젝트명이나 엔드포인트를 하드코딩하지 않았다. 키가 없으면 경고 후 트레이싱 없이 실행한다.
- 모든 trace에 메타데이터와 태그를 붙인다: `scenario_id`, `variant`(baseline/v1…), `run_set`(KST 타임스탬프), `model`, `role`(agent/improver/judge).
- 에이전트는 질문 텍스트만 받아 자기 시나리오 ID를 모른다. 그래서 시나리오 ID는 실행 스크립트가 metadata로 넣는다.
- OpenRouter처럼 OpenAI가 아닌 base_url에서는 스트리밍 토큰 사용량이 기본으로 꺼져 있다. 그래서 `stream_usage=True`로 토큰을 수집했다(응답 내용에는 영향 없음). 비용은 OpenRouter 모델 가격표로 계산한다.

### 2.2 헤드리스 실행과 정답 격리

`eval/run_scenarios.py`는 레포를 레포 밖 임시 샌드박스로 복사하고(`eval/`·`runs/`·`.env`·`.git` 제외), 시나리오마다 새 thread와 새 workspace로 실행한다. 이전에는 정답을 막는 방법이 셸 허용 목록뿐이었다. 이제는 실행 경로 자체에 정답 파일이 없다.

### 2.3 작업 방식 지표

강의의 "작업 방식의 품질" 확인 항목을 지표로 옮겼다.

| 강의 확인 항목 | 지표 |
|---|---|
| 계획 없이 바로 긴 답변을 만들지 않았는가 | SKILL 먼저 읽음, LLM·도구 단계 수 |
| 같은 파일·도구를 의미 없이 반복하지 않았는가 | 같은 도구·인자 반복 수, 도구별 호출 횟수 |
| 실패한 tool을 같은 방식으로 계속 재시도하지 않았는가 | 도구 실패 수, 실패 후 같은 인자 재시도 수 |
| 필요한 정보만 찾아 재사용하는가 | 토큰, latency, 비용 |
| 안전 | eval 접근 시도, 쓰기성 명령 시도 |

지표는 세 출처에서 같은 방식으로 계산한다: 실행 중 LangChain 콜백, LangSmith trace(`metrics --source langsmith`), 대화 메시지. 같은 실행을 로컬 기록과 LangSmith trace에서 각각 계산했을 때 단계 수·토큰·도구 호출 수가 일치하는 것을 확인했다.

## 3. 평가 세트(S1~S4)와 Judge 설계

### 3.1 평가 세트 점검

기존 S1~S4와 answer_key를 그대로 썼다. answer_key 형식(문의 / 문제 지점 / 핵심 근거 / 원인 후보 기대 순위 / 영향 범위 / 반드시 언급 / 언급하면 안 되는 것 / 기대 행동)은 Judge 입력으로 충분했다. 판정이 모호한 부분은 answer_key를 고치지 않고 `eval/rubric.md`에 해석 기준으로 보완했다.

| 모호한 점 | rubric 보완 |
|---|---|
| 핵심 근거가 7~8개일 때 몇 개를 맞춰야 하는가 | 문제 지점을 직접 입증하는 결정적 근거의 과반이면 True. 줄번호 ±2 허용, 경로 접두어 생략 허용, 파일명만 있으면 False |
| 원인 후보 2순위 이하 순서 | 1순위 일치만 엄격히 보고, "근거 부족·원인 아님" 후보가 1순위면 False |
| S4 "판단 보류"의 순위 판정 | 원인을 하나로 정하지 않고 보류·자료 부족을 명시하면 True |
| Judge는 원본을 못 보는데 "원본에 없는 값"을 어떻게 보나 | answer_key와 모순되는 값, 없다고 한 오류를 만든 경우, 근거 없는 [확인]만 False. 검증할 수 없는 값은 감점하지 않고 evidence에 기록 |
| 원인 단정 vs [확인] 표기 | answer_key가 [확인]으로 둔 사실을 [확인]으로 쓰는 것은 단정이 아님 |
| 6단 순서에 추가 섹션 | 6개 섹션이 모두 있고 순서대로면 앞뒤 추가 섹션은 허용 |
| 기대 행동의 반영 위치 | "시나리오별 함정 처리" 항목에 포함 |
| 로그 원본의 이상한 값(`19:63:03.200`) | 원본을 그대로 옮긴 값은 감점하지 않음(목업 로그에 실제로 있는 값) |

### 3.2 Judge

| 형태 | 구현 |
|---|---|
| (b) 항목별 True/False | 9개 항목마다 `passed`·보고서 인용 `evidence`·`reason`을 JSON 스키마로 받음. 반드시 언급 커버리지를 보조 지표로 받음 |
| (a) 종합 점수 | 1~5점과 이유(rubric의 점수 기준표) |
| (c) Pairwise | 같은 시나리오의 A·B를 A·B 순서와 B·A 순서로 두 번 판정. 두 번 모두 같은 보고서를 고를 때만 승리, 엇갈리면 무승부 |

- 모델은 temperature 0, structured output(JSON 스키마)이다. 원래는 에이전트와 다른 모델(Claude·GPT·Gemini)을 쓰려 했다. 그런데 실습용 OpenRouter 워크스페이스 guardrail이 `moonshotai/kimi-k3` 외 모델을 모두 막아서, Judge도 kimi-k3를 temperature 0으로 쓴다. `JUDGE_MODEL_NAME` 하나로 바꿀 수 있다.
- answer_key는 Judge 프롬프트에만 들어간다.
- LangSmith: Dataset `log-trace-eval-s1-s4`(input=question, reference=answer_key, 이미 있으면 예제 갱신). `evaluate()`로 Experiment `<variant>-<run_set>`을 만들어, 9개 항목·종합 점수·trace 지표 evaluator를 시나리오별로 붙인다. 에이전트를 다시 돌리지 않고 저장된 보고서를 target 출력으로 쓰며, 각 행에 원래 에이전트 trace 링크를 넣는다. 원래 trace에도 `judge_*` feedback을 붙인다.

### 3.3 Judge 신뢰도

- **사람 판정과의 일치**: baseline 보고서 S2·S3의 18개 항목을 answer_key·rubric·원본 로그와 대조해 직접 판정했다. Judge와 18/18 일치했다(`runs/20261001-152522/baseline/agreement.md`). 다만 이 수동 판정은 Judge 결과를 본 뒤에 한 검토라 블라인드가 아니다. 사용자의 독립 판정으로 다시 확인할 필요가 있다.
- **재현성**: 같은 보고서 4개를 다시 채점했을 때 36개 항목 판정이 모두 같았다.

## 4. Meta-Harness 실행 주체와 사이클 기록

### 4.1 실행 주체: 방식 A (별도 개선 에이전트)

| | 방식 A: 별도 `harness-improver` 그래프 (채택) | 방식 B: log-trace에 자기개선 모드 |
|---|---|---|
| 장점 | log-trace 프롬프트가 그대로라 회귀 위험이 없다. 셸 권한을 그래프 단위로 줄 수 있다(개선 에이전트만 CLI 허용, 환경변수 토글 불필요). 정답 격리 범위가 분명하다 | 강의의 "하네스가 스스로 사이클을 수행"에 더 가깝다 |
| 단점 | 그래프·프롬프트를 하나 더 관리해야 한다. 같은 모델의 프롬프트 프로필이 섞이지 않게 처리해야 한다 | 프롬프트 변경 자체가 실험 변수가 되어 S1~S4 회귀 확인이 필요하다. 로그 분석 중에도 CLI 셸 권한이 열린다 |

구현 요점:

- 개선 에이전트는 `workspace_improver/`와 meta-harness 스킬만 보고, 셸은 `date`와 meta-harness CLI만 쓴다.
- deepagents는 프롬프트 프로필을 모델 단위로 등록한다. 그래서 그래프를 만드는 동안에만 개선 에이전트 프로필을 등록하고 원래대로 되돌린다.
- meta-harness CLI에 `run --suite`·`compare --suite`·`show --suite`를 추가해 Phase 1 실행 스크립트와 Phase 2 Judge에 연결했다. 개선 에이전트에게는 항목 통과 여부·점수·pairwise 승패·trace 지표만 보여주고, answer_key를 담을 수 있는 Judge 근거·이유는 보여주지 않는다.
- 정답 유출 경로를 추가로 막았다: CLI 입력 파일(`--find-file`·`--replace-file`·`--query-file`)의 `eval/`·`runs/` 경로, `show`의 경로 탈출.
- 최소 변경 원칙을 강화했다: `edit`는 노브 3개만 고칠 수 있고, 새로 넣는 텍스트에 캠페인 ID·`파일:줄번호`·구체 수치가 있으면 과적합으로 거부한다.

### 4.2 사이클 기록

상세 기록은 [improvement_log.md](improvement_log.md)에 있다.

| 사이클 | 진단 | 가설·변경(노브) | 결과 | 판정 |
|---|---|---|---|---|
| 1 | S2 "영향 범위 판단"이 baseline 두 번 모두 False | log-trace 스킬 9번 절차 1줄: 영향 범위는 다른 캠페인을 실제로 조회해 확정하고, 미확인이면 '확인 필요'로 표시 | S2 개선 없음, S3 항목 회귀 2건, pairwise S1·S2 v1 우세 / S4 baseline 우세 | **무승부 → promote 안 함** |

개선 에이전트는 doctor → init → baseline 실행 → 진단 → fork → edit → diff → v1 실행까지 스스로 수행했다. v1의 `--repeat 2`는 1회차가 거의 끝났을 때 **너무 오래 걸려 중단**했다. 남은 S3 채점과 비교는 수동으로 마무리했다.

**고도화 후에도 오래 걸렸던 점과 앞으로의 개선 방향**: baseline 실행부터 v1 1회차까지 약 13분이 걸렸다. 개선 에이전트 세션이 LangSmith에서 하나의 긴 trace로 이어졌다. 다음에는 아래처럼 바꾸려 한다.

- 이미 측정한 baseline을 재사용한다.
- 바뀐 시나리오만 반복 실행한다.
- 평가 세트 실행을 백그라운드 작업과 상태 조회로 분리하고, 사이클마다 trace를 나눈다.
- 항목 판정이 같은 시나리오는 pairwise를 생략한다.
- 강제 종료할 때도 trace를 닫는다.

- 같은 baseline을 두 번 실행했을 때 S3가 6/9 → 9/9로 흔들렸다. 4개 시나리오, 1회 실행으로는 스킬 한 줄 변경의 효과를 노이즈와 구분할 수 없다.
- v1은 겨냥한 S2 영향 범위를 고치지 못했고 다른 시나리오에서 회귀·패배가 섞였다. 기본값 무승부 원칙대로 본체는 baseline-v0 동작을 유지한다.
- 이번 고도화의 실제 성과는 에이전트 점수 상승이 아니다. **평가 엔진을 갖춘 것**이다. 같은 변경을 근거(항목·pairwise·trace 지표·반복)로 기각할 수 있게 되었고, 강의 결론처럼 평가가 다음 가설(v2)을 정하는 기준이 되었다.

### 사용자 재실행 비교 (Phase 4)

LangSmith Studio에서 S1~S4를 새 thread로 직접 실행한 뒤, README의 "Studio에서 직접 실행한 보고서를 baseline-v0과 비교하기" 명령(`run_scenarios.py save` → `judge.py score` → `judge.py compare --a runs/20261001-152522/baseline`)으로 이 표에 결과를 추가한다.

## 6. 한계와 VDI 적용 시 고려사항

### 한계

- **평가 세트 규모**: 시나리오 4개라 한 번의 개선이 우연인지 가리기 어렵다. 반복 실행과 "기본값 무승부"로 보완했지만, 통계적으로 의미 있는 비교에는 시나리오를 더 늘려야 한다.
- **Judge 모델**: guardrail 때문에 Judge가 에이전트와 같은 모델이다. 자기 선호 편향이 있을 수 있다. 사람 판정 일치 18/18도 표본이 작고 블라인드가 아니다. 허용되는 다른 모델로 `JUDGE_MODEL_NAME`을 바꾸고, 사람이 독립적으로 판정한 결과로 다시 확인해야 한다.
- **Judge는 원본을 보지 않는다**: answer_key 밖의 값이 맞는지 검증하지 못한다. "원본에 없는 값" 항목은 모순·없는 오류 생성만 잡는다.
- **비결정성**: 에이전트 모델은 temperature를 지정하지 않아 실행마다 보고서가 달라진다. baseline 두 번의 실행 차이가 곧 노이즈 수준이다.
- **비용 지표**: OpenRouter 가격표 기반 추정이며 캐시·추론 토큰 단가 차이로 LangSmith 표시 비용과 약간 다르다.
- **목업 데이터 특성**: 로그에 `19:63` 같은 비정상 시각이 있다. mock_data는 수정하지 않는다는 원칙에 따라 rubric으로만 처리했다.

### VDI 적용 시 고려사항

- **교체 경계**: `MockRepository`만 실제 읽기 전용 DB·소스 인덱스로 바꾼다. 도구 이름·인자 계약을 유지하면 프롬프트·스킬·평가 코드는 그대로 쓸 수 있다.
- **트레이싱**: LangSmith는 외부 SaaS다. 실제 로그·고객 데이터가 trace input/output에 실리므로, 사내 승인 전에는 `LANGSMITH_TRACING=false`로 끄거나 자체 호스팅 엔드포인트를 쓴다. 지표는 로컬 콜백 기록만으로도 계산된다.
- **Judge와 정답**: 실제 업무 문의에는 answer_key가 없다. VDI에서는 과거 장애 처리 이력으로 정답 세트를 만들고, 담당자가 판정한 결과로 rubric을 맞춘다.
- **격리**: 샌드박스·셸 허용 목록·읽기 전용 도구는 그대로 가져간다. meta-harness의 promote는 사람 승인과 코드 리뷰를 거친다.
- **모델 차이**: VDI에서 쓸 수 있는 모델이 다르면 baseline부터 다시 측정한다. 같은 모델로 고정한 상태에서만 전후를 비교한다.
