# 로그 추적 에이전트 고도화 보고서 (초안)

- 과정: LLM 기반 Agent 구축 및 평가 실습 Day 2 Final 실습
- 대상: 로그 기반 원인 추적 에이전트(`deepagent` 그래프, 모델 `moonshotai/kimi-k3`)
- 기준점: 고도화 전 원본 에이전트(git tag `baseline-v0`), 기준 점수 `runs/20261001-152522/baseline`

## 0. 배경 — 이 에이전트는 무엇이었나

### 0.1 왜 이 에이전트를 만들었나

내 업무는 VDI 환경에서 이루어지고, 소스·로그 같은 업무 데이터는 보안 관리 대상이라 외부로 가지고 나올 수 없다. 대신 이전 프로젝트에서 VDI 안에 소스를 구조화한 Graph DB 같은 조회 기반을 만들어 둔 경험이 있다. 그래서 이번 실습은 업무 데이터를 들고 나와 에이전트를 만드는 대신 다음 순서로 진행했다.

1. 외부(Codespace)에서 에이전트 설계(system prompt, AGENTS.md, skill, 도구 인터페이스)를 목업 데이터로 만들고 검증한다.
2. 검증된 설계와 코드 구조만 VDI로 가지고 들어간다.
3. VDI 안에서 목업 데이터를 읽던 도구를 실제 DB·로그·소스 조회로 바꿔 연결한다.

내 업무 중 **채널 발송 연계 흐름 분석·점검**과 **장애 대응**은 둘 다 로그에서 출발해 흩어진 배치·모듈·소스를 따라가며 문제 지점을 찾는 일이다. 배치와 모듈이 흩어져 있어 어디서 막혔는지 연결고리를 찾기 어렵다. 대응 속도와 품질도 담당자 역량에 따라 크게 달라진다. 그래서 두 업무를 하나로 묶어 **로그 기반 원인 추적 에이전트**를 만들었고, 첫 적용 범위는 범위가 정해져 있고 검증하기 쉬운 채널 발송 연계로 좁혔다.

### 0.2 원래 설계 (1일차 기획)

- **PoC 주제**: 채널 발송 배치 로그와 기획자 문의를 받으면, 발송 흐름의 어느 단계에서 문제가 생겼는지 추적하고, 원인 후보와 확인 순서를 정리한 분석 보고서 초안을 만든다.
- **역할 분담**: 에이전트는 "로그·문의에서 핵심 추출 → 관련 소스 찾기 → 흐름 요약 → 문서 초안"의 앞단만 맡는다. 최종 원인 판단, 소스 수정, 배치 재실행 같은 조치는 담당자가 한다.
- **입력(모두 목업)**: 채널 발송 배치 로그(B01 대상 추출 → B02 오퍼 할당 → B03 메시지 생성 → B04 채널 발송, R01 결과 수신 → R02 성과 집계), 배치 잡 목록, 연계 모듈 가상 Java 소스, 발송 이력·집계 테이블, 변경 이력, 과거 장애 이력
- **도구**: MCP를 붙일 수 없어서, 목업 파일을 읽는 읽기 전용 조회 도구 10개로 대신했다. 도구 이름·입력·출력은 실제 연결을 가정해 설계했다. 그래서 VDI에서는 `MockRepository` 내부 구현만 실제 발송 이력 DB, 소스·Graph DB, 장애 이력으로 바꾸면 된다.
- **규칙**
  - 원본에 없는 값을 쓰지 않는다.
  - 원인은 "원인 후보"로만 쓴다.
  - 조치는 제안까지만 하고, DB는 조회만 한다.
  - 개인정보는 마스킹한다.
  - 자료가 부족하면 지어내지 않고 추가 자료를 요청한다.
  - 과거 사례는 같은 점과 다른 점을 함께 적는다.
- **출력**: ① 요약 → ② 발송 흐름 정리 → ③ 문제 발생 지점과 근거 로그 → ④ 원인 후보 → ⑤ 확인 순서 체크리스트 → ⑥ 유사 과거 사례의 6단 보고서. 모든 판단에 `파일:줄` 근거를 달고 [확인]과 [추정]을 구분한다.
- **1일차 구현**: 위 규칙을 시스템 프롬프트에 넣고, 숙련자의 추적 순서를 `log-trace` 스킬(13단계 절차·발송 흐름 참고자료·마스킹 규칙·보고서 양식)로 정리했다. 평가용 시나리오 4개(아래)와 정답 기준을 만들고, 사람이 9개 항목 판정표를 직접 채워 평가했다.

| 시나리오 | 기획자 문의 | 에이전트가 찾아야 할 것 |
|---|---|---|
| S1 | 9/23 캠페인이 발송이 안 된 것 같다 | 처리 지연으로 자정을 넘겨 발송일 검증에 실패하고 전체 롤백됨 |
| S2 | 결과 화면에 오퍼 성공 건수가 안 보인다 | 배포 후 집계 배치가 이전 테이블을 계속 읽어 0으로 집계됨 |
| S3 | 대상이 예상보다 너무 적다 | 장애가 아니라 피로도 등 제외 규칙이 정상 적용된 것 |
| S4 | 일부만 발송된 것 같다 | 로그가 중간에 끊겨 원인 판단 보류, 추가 자료 요청 |

### 0.3 1일차 설계의 한계와 2일차 과제

1일차 에이전트는 동작은 했지만 세 가지를 알 수 없었다.

- 보고서가 왜 그렇게 나왔는지(어떤 도구를 몇 번 썼는지, 비용·시간이 얼마였는지)
- 평가가 맞는지(사람이 손으로 채운 판정표, 근거 기록 없음)
- 프롬프트나 스킬을 고쳤을 때 정말 나아졌는지

2일차 강의(Observation, LLM-as-a-Judge, Meta-Harness)는 이 세 가지를 정확히 다룬다. 이 보고서는 그 세 가지를 붙인 과정과 결과다.

### 0.4 이 보고서에서 쓰는 이름

| 이름 | 뜻 |
|---|---|
| **원본 에이전트** (baseline, git tag `baseline-v0`) | 1일차에 만든 에이전트 그대로. 2일차에는 관측 기능만 붙였고 행동(프롬프트·스킬·도구)은 바꾸지 않았다 |
| **원본 1차 측정** | 원본 에이전트를 처음 실행·채점한 결과(`runs/20261001-152522`). 모든 비교의 기준 점수 |
| **원본 2차 측정** | 같은 원본 에이전트를 개선 에이전트가 다시 실행한 결과(`runs/20261001-154636`). 1차와의 차이가 곧 "같은 에이전트도 실행마다 흔들리는 폭"이다 |
| **개선안 1** (variant `v1`) | 개선 에이전트가 만든 수정본. log-trace 스킬 한 줄에 "영향 범위는 다른 캠페인을 실제로 조회해 확인한다"를 추가했다(`runs/20261001-155256`) |
| **개선 에이전트** (`harness-improver`) | 원본 에이전트를 복제해 고쳐 보고 비교하는 두 번째 에이전트 |
| **Judge** | 보고서를 정답 기준과 대조해 채점하는 LLM 평가자 |

| **promote** | 개선안을 원본 에이전트에 실제로 반영하는 것. 확실히 나을 때만, 사람 승인 후에 한다 |

## 1. 개요

1일차에 만든 로그 추적 에이전트(원본 에이전트)를 세 단계로 고도화했다.

| 단계 | 한 일 | 결과물 |
|---|---|---|
| Observation | LangSmith 트레이싱, 시나리오 메타데이터, 작업 방식 지표 | `observability.py`, `eval/run_scenarios.py`, `eval/trace_metrics.py` |
| 평가 세트·Judge | 기존 S1\~S4를 Dataset으로 올리고, 수동 9개 항목 판정을 LLM Judge로 전환 | `eval/judge.py`, `eval/rubric.md`, Dataset `log-trace-eval-s1-s4` |
| Meta-Harness | 별도 개선 에이전트가 격리 복제본으로 실행·수정·비교 | `harness_improver.py`, meta-harness `--suite` 모드, `docs/improvement_log.md` |

핵심 원칙은 강의 결론인 "평가가 개선의 엔진이 된다"이다. 하네스를 손으로 고치지 않았다. 개선 에이전트가 스킬을 읽고 CLI로 자기 복제본을 실행하고, Judge 점수와 trace 지표를 근거로 판정하게 했다.

## 2. Observation 구성

### 2.1 트레이싱

- `.env`의 `LANGSMITH_TRACING`·`LANGSMITH_API_KEY`·`LANGSMITH_PROJECT=log-trace-agent`·`LANGSMITH_ENDPOINT`만으로 동작한다. 코드에 프로젝트명이나 엔드포인트를 하드코딩하지 않았다. 키가 없으면 경고 후 트레이싱 없이 실행한다.
- 모든 trace에 메타데이터와 태그를 붙인다: `scenario_id`, `variant`(baseline/v1…), `run_set`(KST 타임스탬프), `model`, `role`(agent/improver/judge).
- 에이전트는 질문 텍스트만 받아 자기 시나리오 ID를 모른다. 그래서 시나리오 ID는 실행 스크립트가 metadata로 넣는다.
- OpenRouter처럼 OpenAI가 아닌 base_url에서는 스트리밍 토큰 사용량이 기본으로 꺼져 있다. 그래서 `stream_usage=True`로 토큰을 수집했다(응답 내용에는 영향 없음). 비용은 OpenRouter 모델 가격표로 계산한다.

### 2.2 헤드리스 실행과 정답 격리

`eval/run_scenarios.py`는 레포를 레포 밖 임시 샌드박스로 복사하고(`eval/`·`runs/`·`.env`·`.git` 제외), 시나리오마다 새 thread와 새 workspace로 실행한다. 이전에는 정답을 막는 방법이 셸 허용 목록뿐이었다. 이제는 실행 경로 자체에 정답 파일이 없다.

### 2.3 작업 방식 지표

강의의 "작업 방식의 품질" 확인 항목을 지표로 옮겼다.

| 강의 확인 항목 | 지표 |
|---|---|
| 계획 없이 바로 긴 답변을 만들지 않았는가 | SKILL 먼저 읽음, LLM·도구 단계 수 |
| 같은 파일·도구를 의미 없이 반복하지 않았는가 | 같은 도구·인자 반복 수, 도구별 호출 횟수 |
| 실패한 tool을 같은 방식으로 계속 재시도하지 않았는가 | 도구 실패 수, 실패 후 같은 인자 재시도 수 |
| 필요한 정보만 찾아 재사용하는가 | 토큰, latency, 비용 |
| 안전 | eval 접근 시도, 쓰기성 명령 시도 |

지표는 세 출처에서 같은 방식으로 계산한다: 실행 중 LangChain 콜백, LangSmith trace(`metrics --source langsmith`), 대화 메시지. 같은 실행을 로컬 기록과 LangSmith trace에서 각각 계산했을 때 단계 수·토큰·도구 호출 수가 일치하는 것을 확인했다.

## 3. 평가 세트(S1\~S4)와 Judge 설계

### 3.1 평가 세트 점검

기존 S1\~S4와 answer_key를 그대로 썼다. answer_key 형식(문의 / 문제 지점 / 핵심 근거 / 원인 후보 기대 순위 / 영향 범위 / 반드시 언급 / 언급하면 안 되는 것 / 기대 행동)은 Judge 입력으로 충분했다. 판정이 모호한 부분은 answer_key를 고치지 않고 `eval/rubric.md`에 해석 기준으로 보완했다.

| 모호한 점 | rubric 보완 |
|---|---|
| 핵심 근거가 7\~8개일 때 몇 개를 맞춰야 하는가 | 문제 지점을 직접 입증하는 결정적 근거의 과반이면 True. 줄번호 ±2 허용, 경로 접두어 생략 허용, 파일명만 있으면 False |
| 원인 후보 2순위 이하 순서 | 1순위 일치만 엄격히 보고, "근거 부족·원인 아님" 후보가 1순위면 False |
| S4 "판단 보류"의 순위 판정 | 원인을 하나로 정하지 않고 보류·자료 부족을 명시하면 True |
| Judge는 원본을 못 보는데 "원본에 없는 값"을 어떻게 보나 | answer_key와 모순되는 값, 없다고 한 오류를 만든 경우, 근거 없는 [확인]만 False. 검증할 수 없는 값은 감점하지 않고 evidence에 기록 |
| 원인 단정 vs [확인] 표기 | answer_key가 [확인]으로 둔 사실을 [확인]으로 쓰는 것은 단정이 아님 |
| 6단 순서에 추가 섹션 | 6개 섹션이 모두 있고 순서대로면 앞뒤 추가 섹션은 허용 |
| 기대 행동의 반영 위치 | "시나리오별 함정 처리" 항목에 포함 |
| 로그 원본의 이상한 값(`19:63:03.200`) | 원본을 그대로 옮긴 값은 감점하지 않음(목업 로그에 실제로 있는 값) |

### 3.2 Judge

| 형태 | 구현 |
|---|---|
| (b) 항목별 True/False | 9개 항목마다 `passed`·보고서 인용 `evidence`·`reason`을 JSON 스키마로 받음. 반드시 언급 커버리지를 보조 지표로 받음 |
| (a) 종합 점수 | 1\~5점과 이유(rubric의 점수 기준표) |
| (c) Pairwise | 같은 시나리오의 A·B를 A·B 순서와 B·A 순서로 두 번 판정. 두 번 모두 같은 보고서를 고를 때만 승리, 엇갈리면 무승부 |

- 모델은 temperature 0, structured output(JSON 스키마)이다. 원래는 에이전트와 다른 모델(Claude·GPT·Gemini)을 쓰려 했다. 그런데 실습용 OpenRouter 워크스페이스 guardrail이 `moonshotai/kimi-k3` 외 모델을 모두 막아서, Judge도 kimi-k3를 temperature 0으로 쓴다. `JUDGE_MODEL_NAME` 하나로 바꿀 수 있다.
- answer_key는 Judge 프롬프트에만 들어간다.
- LangSmith: Dataset `log-trace-eval-s1-s4`(input=question, reference=answer_key, 이미 있으면 예제 갱신). `evaluate()`로 Experiment `<variant>-<run_set>`을 만들어, 9개 항목·종합 점수·trace 지표 evaluator를 시나리오별로 붙인다. 에이전트를 다시 돌리지 않고 저장된 보고서를 target 출력으로 쓰며, 각 행에 원래 에이전트 trace 링크를 넣는다. 원래 trace에도 `judge_*` feedback을 붙인다.

### 3.3 Judge 신뢰도

- **사람 판정과의 일치**: 원본 1차 측정 보고서 S2·S3의 18개 항목을 answer_key·rubric·원본 로그와 대조해 직접 판정했다. Judge와 18/18 일치했다(`runs/20261001-152522/baseline/agreement.md`). 다만 이 수동 판정은 Judge 결과를 본 뒤에 한 검토라 블라인드가 아니다. 사용자의 독립 판정으로 다시 확인할 필요가 있다.
- **재현성**: 같은 보고서 4개를 다시 채점했을 때 36개 항목 판정이 모두 같았다.

### 3.4 원본 에이전트의 기준 점수 (원본 1차 측정)

| 항목 | S1 | S2 | S3 | S4 |
|---|---|---|---|---|

구현 요점:

- 개선 에이전트는 `workspace_improver/`와 meta-harness 스킬만 보고, 셸은 `date`와 meta-harness CLI만 쓴다.
- deepagents는 프롬프트 프로필을 모델 단위로 등록한다. 그래서 그래프를 만드는 동안에만 개선 에이전트 프로필을 등록하고 원래대로 되돌린다.
- meta-harness CLI에 `run --suite`·`compare --suite`·`show --suite`를 추가해 Phase 1 실행 스크립트와 Phase 2 Judge에 연결했다. 개선 에이전트에게는 항목 통과 여부·점수·pairwise 승패·trace 지표만 보여주고, answer_key를 담을 수 있는 Judge 근거·이유는 보여주지 않는다.
- 정답 유출 경로를 추가로 막았다: CLI 입력 파일(`--find-file`·`--replace-file`·`--query-file`)의 `eval/`·`runs/` 경로, `show`의 경로 탈출.
- 최소 변경 원칙을 강화했다: `edit`는 노브 3개만 고칠 수 있고, 새로 넣는 텍스트에 캠페인 ID·`파일:줄번호`·구체 수치가 있으면 과적합으로 거부한다.

- 이미 측정한 원본 점수를 재사용한다(매 사이클 원본을 다시 돌리지 않는다).
- 바뀐 시나리오만 반복 실행한다.

- 항목 판정이 같은 시나리오는 pairwise를 생략한다.
- 강제 종료할 때도 trace를 닫는다.

### 5.1 고도화 후 무엇이 얼마나 나아졌나

**에이전트의 답변 품질은 아직 올라가지 않았다.** 원본 에이전트의 S1\~S4 통과 항목은 1차 측정에서 36개 중 32개(89%), 같은 에이전트를 다시 돌린 2차 측정에서 35개(97%)였다. 스킬 한 줄을 고친 개선안 1은 33개(92%)였다. 숫자만 보면 오르내림이 있지만, 이 차이는 같은 에이전트를 두 번 돌렸을 때 생기는 흔들림(S3에서 3개 항목) 범위 안이다. 그래서 개선됐다고 말할 수 없다. 오히려 개선안 1은 단계 수·토큰·비용이 10\~40% 늘었다. "더 조회하라"는 지시가 품질은 못 올리고 비용만 키운 것이다. 고도화 전이었다면 이 변경을 "영향 범위를 더 꼼꼼히 보게 했으니 좋아졌을 것"이라고 보고 그대로 반영했을 수 있다. 이번에는 근거를 보고 반영하지 않기로 판단했다.

**크게 나아진 것은 에이전트를 평가하고 개선하는 방식이다.**

- **평가 시간과 일관성**: 고도화 전에는 보고서 4개를 사람이 정답 파일과 하나씩 대조하며 36칸 판정표를 손으로 채웠다. 근거도 남지 않았다. 이제는 명령 하나로 S1\~S4를 동시에 실행하고(시나리오당 40\~110초, 약 $0.11\~0.20, 전체 약 2분·$0.6), 채점도 명령 하나로 1\~2분 안에 끝난다. 모든 판정에는 보고서 인용 근거와 이유가 붙는다. 같은 보고서를 다시 채점해도 36개 판정이 모두 같았다. 직접 대조한 18개 항목도 Judge와 모두 일치했다.
- **보이지 않던 작업 방식이 숫자로 보인다**: 이전에는 최종 보고서만 볼 수 있었다. 이제는 시나리오마다 몇 단계를 거쳤는지, 같은 도구를 반복했는지, 실패를 같은 방식으로 재시도했는지, 토큰·시간·비용이 얼마였는지, 스킬을 먼저 읽었는지, 정답이나 쓰기 명령을 시도했는지를 표와 LangSmith trace로 바로 확인한다. baseline 측정 결과 반복 호출·실패 재시도·정답 접근·쓰기 시도는 모두 0이었다. 따라서 작업 방식보다는 판단의 질(영향 범위, 정상 규칙과 결함의 구분)이 다음 개선 대상이라는 것이 분명해졌다.
- **정답 유출 위험 감소**: 이전에는 셸 허용 목록 하나에 의존했다. 이제는 에이전트를 정답 파일이 없는 레포 밖 폴더에서 실행한다. 개선 에이전트가 정답을 읽을 수 있었던 경로 3곳(입력 파일 지정, 결과 조회 경로 탈출, Judge 근거 노출)도 막았다.
- **개선의 근거화**: 개선 에이전트가 스스로 진단 → 가설 → 한 줄 수정 → 재실행 → 비교까지 수행했다. 결과는 "개선 없음·회귀 혼재 → 무승부"라는 근거 있는 판정으로 정리되었다. 평가 세트가 작고 결과가 흔들린다는 사실도 이 과정에서 드러났다. 그래서 다음 개선은 프롬프트보다 반복 실행 횟수와 실행 시간 단축이 먼저라는 방향이 잡혔다.

정리하면, 이번 고도화는 에이전트를 더 똑똑하게 만든 단계가 아니다. **에이전트가 실제로 좋아졌는지 판단할 수 있는 체계를 만든 단계**다. 남은 과제는 두 가지다. 하나는 개선안 1처럼 효과 없는 변경을 걸러내는 지금의 체계로 개선안 2 가설(결과 흐름에서 영향받은 날짜를 배치 이력으로 역산)을 시험해 점수를 실제로 올리는 것이다. 다른 하나는 사이클 한 번에 13분이 걸린 실행 시간을 줄이는 것이다.

## 6. 한계와 VDI 적용 시 고려사항

### 한계

- **평가 세트 규모**: 시나리오 4개라 한 번의 개선이 우연인지 가리기 어렵다. 반복 실행과 "기본값 무승부"로 보완했지만, 통계적으로 의미 있는 비교에는 시나리오를 더 늘려야 한다.
- **Judge 모델**: guardrail 때문에 Judge가 에이전트와 같은 모델이다. 자기 선호 편향이 있을 수 있다. 사람 판정 일치 18/18도 표본이 작고 블라인드가 아니다. 허용되는 다른 모델로 `JUDGE_MODEL_NAME`을 바꾸고, 사람이 독립적으로 판정한 결과로 다시 확인해야 한다.
- **Judge는 원본을 보지 않는다**: answer_key 밖의 값이 맞는지 검증하지 못한다. "원본에 없는 값" 항목은 모순·없는 오류 생성만 잡는다.
- **비결정성**: 에이전트 모델은 temperature를 지정하지 않아 실행마다 보고서가 달라진다. 원본 에이전트를 두 번 실행한 차이(1차·2차 측정)가 곧 노이즈 수준이다.
- **비용 지표**: OpenRouter 가격표 기반 추정이며 캐시·추론 토큰 단가 차이로 LangSmith 표시 비용과 약간 다르다.
- **목업 데이터 특성**: 로그에 `19:63` 같은 비정상 시각이 있다. mock_data는 수정하지 않는다는 원칙에 따라 rubric으로만 처리했다.

### VDI 적용 시 고려사항

- **교체 경계**: `MockRepository`만 실제 읽기 전용 DB·소스 인덱스로 바꾼다. 도구 이름·인자 계약을 유지하면 프롬프트·스킬·평가 코드는 그대로 쓸 수 있다.
- **트레이싱**: LangSmith는 외부 SaaS다. 실제 로그·고객 데이터가 trace input/output에 실리므로, 사내 승인 전에는 `LANGSMITH_TRACING=false`로 끄거나 자체 호스팅 엔드포인트를 쓴다. 지표는 로컬 콜백 기록만으로도 계산된다.
- **Judge와 정답**: 실제 업무 문의에는 answer_key가 없다. VDI에서는 과거 장애 처리 이력으로 정답 세트를 만들고, 담당자가 판정한 결과로 rubric을 맞춘다.
- **격리**: 샌드박스·셸 허용 목록·읽기 전용 도구는 그대로 가져간다. meta-harness의 promote는 사람 승인과 코드 리뷰를 거친다.
- **모델 차이**: VDI에서 쓸 수 있는 모델이 다르면 원본 에이전트 점수부터 다시 측정한다. 같은 모델로 고정한 상태에서만 전후를 비교한다.
