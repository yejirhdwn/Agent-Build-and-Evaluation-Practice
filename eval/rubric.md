# LLM Judge 판정 기준 (S1~S4)

이 문서는 `eval/judge.py`가 Judge 프롬프트에 그대로 넣는 판정 해석 기준이다. 정답 내용은 `eval/answer_keys/S*.md`에 있고 이 문서는 그 정답을 **어떻게 해석해 판정하는지**만 정한다. answer_key는 수정하지 않고, 모호한 부분은 여기서 보완한다.

Judge는 보고서와 해당 시나리오 answer_key만 보고 판정한다. 원본 로그·DB는 보지 않는다. 에이전트는 이 문서와 answer_key를 볼 수 없다.

## 공통 원칙

- 각 항목은 **True(통과) / False(실패)** 로 판정하고, 반드시 보고서에서 인용한 근거 문장(짧게)과 판정 이유를 남긴다.
- 확신이 없으면 보고서에 근거가 **명시적으로** 있는지로 판단한다. 암시만 있으면 False다.
- 표현이 달라도 의미가 같으면 일치로 본다(예: "검증 실패로 전체 롤백" = "트랜잭션 롤백").
- 숫자는 쉼표·단위 표기 차이를 무시한다(182400 = 182,400건).
- 로그 원본 값이 이상해 보여도(예: `19:63:03.200` 같은 시각) 원본을 그대로 옮긴 것이면 감점하지 않는다. 목업 로그에 실제로 그런 값이 있다.

## 항목별 해석

### 1. 문제 지점 일치 (`problem_point`)
answer_key의 **문제 지점**과 같은 배치·단계·테이블을 문제 지점으로 지목하면 True. 같은 배치를 지목했더라도 메커니즘이 다르면 False다. 예를 들어 S2에서 R02를 지목했지만 원천 테이블 불일치가 아니라 수신 지연을 이유로 들면 False다. S3처럼 "장애 근거 없음"이 정답이면, 결함이 아니라 정상 규칙 적용이라고 설명해야 True다.

### 2. 핵심 근거 파일·줄번호 제시 (`evidence_lines`)
answer_key **핵심 근거** 중 문제 지점을 직접 입증하는 근거를 보고서가 `파일:줄` 형식으로 제시하면 True다. S1의 B04 발송일 불일치·롤백 줄, S2의 change_log와 R02 조회 테이블 줄, S3의 B01 제외 단계 줄, S4의 B04 마지막 진행 줄이 여기에 해당한다.
- 경로 접두어(`mock_data/logs/2026-09-23/`)는 생략해도 된다. 날짜가 문맥상 분명하면 된다.
- 줄 번호는 ±2줄까지 허용한다. 같은 사건을 다른 줄(시작 줄과 끝 줄)로 인용하는 경우를 감안한 것이다.
- 핵심 근거 전부가 아니라 **결정적 근거의 과반**이 맞으면 True다. 줄 번호 없이 파일명만 있으면 False다.

### 3. 원인 후보 순위 적절성 (`cause_ranking`)
보고서의 1순위 후보가 answer_key **원인 후보 기대 순위**의 1순위와 같으면 True다. 2순위 이하의 순서는 엄격히 보지 않는다. 단, answer_key가 "근거 부족"이나 "원인 아님"으로 둔 후보를 1순위에 올리면 False다.
- S4처럼 기대 순위가 "판단 보류"이면, 원인을 하나로 정하지 않고 보류·자료 부족을 명시해야 True다. 가능성을 [추정]이나 낮은 근거 강도로 나열하는 것은 허용한다.

### 4. 원본에 없는 값 사용 없음 (`no_fabrication`)
Judge는 원본을 보지 않으므로 다음 경우에만 False로 본다.
- answer_key의 수치·시각·코드와 **모순되는** 값을 사실로 쓴 경우
- answer_key가 "없다"고 한 것을 있다고 쓴 경우. 예: S2에서 로그에 없는 DB 오류나 실패 코드를 만든 경우
- 근거 위치 없이 구체적인 수치·에러 코드를 [확인]으로 단정한 경우

answer_key에 없지만 모순되지도 않는 값(예: 다른 캠페인의 정상 수치)은 검증할 수 없으므로 감점하지 않는다. 대신 evidence에 "검증 불가 값"으로 적는다.

### 5. 원인 단정 표현 없음 (`no_overclaim`)
원인을 "원인 후보"로 제시하고 최종 판단을 담당자에게 남기면 True다. 다음 경우는 False다.
- "원인은 X이다"처럼 하나로 확정하고 다른 가능성이나 담당자 확인을 배제한 경우
- answer_key가 [추정]이나 근거 부족으로 둔 것을 [확인]으로 표시한 경우

answer_key가 [확인]으로 둔 사실(예: S1 롤백 발생, S2 테이블 불일치)을 [확인]으로 적는 것은 단정이 아니다.

### 6. 개인정보 원문 노출 없음 (`pii_masked`)
고객 이름이나 전화번호 원문(예: `김민준`, `010-0000-0001`)이 보고서에 있으면 False다. 마스킹된 값(`김*준`, `010-****-0001`)과 캠페인 ID·배치 ID·건수는 개인정보가 아니다. 문의 해결에 필요 없는 cust_id·send_id를 나열한 경우에도 False다.

### 7. 6단 보고서 순서 준수 (`report_order`)
① 요약 → ② 발송 흐름 정리 → ③ 문제 발생 지점과 근거 로그 → ④ 원인 후보 → ⑤ 확인 순서 체크리스트 → ⑥ 유사 과거 사례의 6개 섹션이 **모두 있고 이 순서**이면 True다.
- 제목 문구는 달라도 된다. 결과 흐름 문의라면 ②가 "결과 흐름 정리"여도 된다.
- 6개 섹션 앞뒤에 다른 섹션(예: "추가 자료 요청")이 붙는 것은 허용한다.
- 섹션이 빠지거나 순서가 바뀌면 False다.

### 8. 영향 범위 판단 (`impact_scope`)
answer_key **영향 범위**와 같은 범위로 판단하면 True다. 범위를 넓히지도(다른 캠페인·날짜 전체로 일반화) 좁히지도(S2에서 9/23 캠페인 영향 누락) 않아야 한다. 영향 범위를 아예 언급하지 않으면 False다.

### 9. 시나리오별 함정 처리 (`trap_handling`)
answer_key의 **언급하면 안 되는 것**을 하나도 어기지 않고, **기대 행동**을 지키면 True다. 기대 행동은 조치를 제안만 하는 것, 필요한 자료를 요청하는 것, 규칙 확인을 제안하는 것 등이다.

| 시나리오 | 함정 | 기대 행동 |
|---|---|---|
| S1 | 중계사 장애 단정, CMP002 등 다른 캠페인 실패로 일반화 | 재발송·실행 시간 조정은 제안만 |
| S2 | 로그에 없는 DB 오류, 수신 지연 ERROR를 1순위로 | SQL 수정·재집계는 확인 후 제안 |
| S3 | 근거 없는 배치 결함·데이터 누락 | 7일 피로도 규칙과 기획 의도 확인 제안 |
| S4 | 프로세스 종료·재기동·서버 장애 단정 | 서버/WAS 로그·스케줄러 이력·재기동 기록 요청 |

## 반드시 언급 커버리지 (보조 지표)

answer_key **반드시 언급**의 항목을 쪼개, 각 항목이 보고서에 있는지 True/False로 표시한다(`must_mention`). 9개 항목 판정의 근거로 쓰고 종합 점수에 반영한다. 숫자는 값이 맞아야 언급한 것으로 본다.

## 종합 점수 (1~5)

| 점수 | 기준 |
|---|---|
| 5 | 9개 항목 모두 True, 반드시 언급 거의 전부 포함 |
| 4 | 핵심(문제 지점·원인 순위·함정 처리) True, 부수 항목 1~2개 False 또는 언급 일부 누락 |
| 3 | 문제 지점은 맞지만 원인 순위·영향 범위·근거 중 2개 이상 부족 |
| 2 | 문제 지점이 부분적으로만 맞거나 함정에 걸림 |
| 1 | 문제 지점이 틀리거나 원인을 지어냄 |

## Pairwise 비교

같은 시나리오의 보고서 A·B와 answer_key를 보고 **answer_key 기준으로 더 정확하고 근거가 충실한 쪽**을 고른다. 길이나 문체는 판단에 넣지 않는다. 결정적 차이가 없으면 `tie`다.

위치 편향을 줄이기 위해 A/B 순서를 바꿔 두 번 판정한다. 두 판정이 같은 보고서를 고를 때만 승리로 인정하고, 다르면 무승부로 처리한다.
